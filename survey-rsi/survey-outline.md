# 从资料库到综述：章节与分类轴

建议以“**物理经验如何形成可验证、可保留的能力更新**”为主线。下面是整理者提出的写作方案，不是某篇论文的结论；阅读卡片是证据单元，章节围绕问题组合多个证据单元。

## 推荐章节骨架

| 章节 | 核心问题 | 可以先用的材料 | 还需要补的证据 |
| :--- | :--- | :--- | :--- |
| 范围与定义 | 哪些是任务内适应、持久自我改进、改进器递归增强？ | [证据对照](evidence-map.md)；Zeva-Ego / MessyMem / RegenHarness 的差异 | 明确跨任务、会话、部署的重置边界；不要靠标题纳入 |
| 策略与世界模型更新 | 执行经验怎样进入参数，模型想象何时可信？ | RAPolicy、ForceRFT、BEE、HiRE、CLAW、InternW0、The Gaussian Is Enough；[世界模型主题](topics.md#world) | 世界模型误差、策略收益、数据来源与旧任务保持的联合评测 |
| 记忆、技能与可执行代码 | 不改基础权重，系统还能更新什么？ | MessyMem、MemBodied、机器人软件学习与迁移、LEMCA、Banana Kick | 记忆/技能清空对照、跨任务迁移、库膨胀与退化 |
| 反馈、目标与自动课程 | 什么决定更新方向和接纳标准？ | No Free Checker、SRPO、AgenticRL、HiRE、Banana Kick | 固定验证器 vs 共同演化验证器；奖励投机与独立任务指标 |
| 连续物理运行的条件 | 学习闭环在硬件上为什么难持续？ | HALTER、LIBERO-RECOVER、SPINE、RegenHarness | 人工接管/复位时长、失败损耗、全天运行与累计成本 |
| 持续学习与跨部署积累 | 新能力增加后旧能力是否保持？ | FAN、MEMOBench、持续世界模型基准 | 多轮前向/后向迁移、场景漂移、旧数据依赖 |
| 从自我改进到递归 | 学习/研究流程自身能否越来越有效？ | 原报告的 STOP、DGM、HELIX、Dream-RSI 等仅作待复核入口；[改进器主题](topics.md#improvers) | 机器人上的外层改进器更新、冻结外层对照与预算匹配 |
| 评价与开放问题 | 什么证据足以支持“越部署越强”？ | CMA、MemBodied、X2Real、经验检索审计、No Free Checker、LIBERO-RECOVER | 多轮改进曲线、独立验收、可复现数据与长期回滚审计 |

上述已审卡片均可从[主题页](topics.md)进入；原报告材料从[既有条目索引](baseline.md)进入，并须先补原文核查。

## 分类维度：不要用单一等级包办所有判断

| 维度 | 可用标签 / 要记录的值 | 为什么有用 |
| :--- | :--- | :--- |
| 更新对象 | 策略、世界模型、奖励、验证器、记忆、技能、代码、harness、数据、环境、形态、改进器 | 区分改进了哪一层 |
| 更新形式 | 梯度、程序编辑、检索写入、搜索选择、结构修改、目标重加权 | 同样叫 evolution，机制可能完全不同 |
| 触发条件 | 每步、每 episode、失败后、周期批次、不确定性门槛、人发起 | 确认系统实际何时学习 |
| 反馈来源 | 环境奖励、物理传感、人工接管/偏好、VLM、世界模型、形式验证 | 识别反馈成本与偏差 |
| 留存范围 | 当前调用、一次尝试、同实例多次、跨任务、跨部署、跨机器人 | 任务内适应与持续积累的关键界线 |
| 重置协议 | 清记忆、不清环境、恢复初态、保留缓存、重新初始化参数 | 排除缓存或任务难度变化造成的假进步 |
| 训练时机 | 离线后训练、在线更新、异步批次、测试时上下文适应 | 避免把离线微调当部署期学习 |
| 自主程度 | 人选任务、人标成败、人接管、人复位、人批准发布 | “自主”需拆成多个环节 |
| 物理证据 | 纯软件、仿真、sim-to-real、真机在线、多机器人车队 | 物理风险与可扩展性不同 |
| 验收独立性 | 自评、同源模型互评、独立验证器、外部传感、盲评 | 防止提议与验证共享错误 |
| 评价对象 | 最终成功、恢复、分支决策、速度、可靠性、能耗、资源成本 | 成功率无法覆盖所有能力 |
| 持续性指标 | 保持率、遗忘、前向迁移、后向迁移、学习速度 | 分开报告获得新能力和保住旧能力 |
| 实验单位 | episode、任务、随机种子、情境对、硬件、受试者 | 避免将重复测量伪装为独立样本 |
| 预算 | 示范小时、交互步、人工时间、GPU时、token、复位/失败成本 | 让“效率提升”具有可比口径 |
| 安全与发布 | 不变约束、沙箱、回归门控、分阶段发布、回滚 | 检查修改是否可控可追溯 |
| 泛化范围 | 新对象、新任务、新动力学、新环境、新本体 | 具体说明能力增长发生在哪里 |
| 递归深度 | 被控策略更新、更新器配置更新、更新规则/研究程序更新 | 不能将任务层闭环直接升级为强 RSI |
| 来源与证据 | 原始论文、会议版本、作者代码、企业自述、观点；全文/摘要/线索 | 标签分开，来源类型不替代质量审计 |

## 三种可选写法

**机制主线（建议作为正文）**：策略 → 模型 → 记忆/技能/代码 → 目标/课程 → 改进器。好处是各类工作有明确位置；通过交叉引用处理多层同时更新的系统。

**物理闭环主线（适合系统图）**：经验采集、反馈构造、候选更新、独立验收、保留/发布、后续执行。每条边标出谁控制、需要什么数据以及在哪里会失败。

**证据主线（适合比较表）**：任务内适应、同任务多轮参数更新、跨任务能力积累、改进器增强。不要画成已经实现的必然发展阶梯；一篇工作可在某一轴强、在另一轴缺证据。

## 可以直接展开的综合论点

- **世界模型、记忆和评测基础设施都可能被误写成RSI。** InternW0部署期只更新上下文，MemBodied主协议每次重置，X2Real更新的是任务与环境；三者应分别列为支撑组件、边界案例与评价基础设施。
- **负结果应进入机制主线。** The Gaussian Is Enough提示复杂先验不一定带来更好微调；综述比较策略后训练时应把编码器可塑性和高斯强基线列为必要对照。
- **持久性比“是否训练基础模型”更关键。** 用 MessyMem 与 2AM、Zeva-Ego 对比记忆的范围；再用 ForceRFT、BEE 展示冻结基础 VLA 下的可学习组件。证据不足的跨会话留存应保留为空。
- **反馈也会成为需要适配的对象。** 用 HiRE、AgenticRL 和 Banana Kick 比较支持集编辑、奖励代码编辑和目标参数更新，但单独说明固定的外层规则。
- **闭环可运行与闭环带来能力增长要分别证实。** 用 HALTER/恢复框架解释运行条件，用 RegenHarness 的案例边界说明发布协议还需要修订收益对照。
- **验证器本身也要被验证。** 连接 No Free Checker、CMA 与经验检索审计，讨论最终成功、记忆敏感性和语义正确性为何不等价。

## 建议准备的图与表

9月24日的[企业案例与Zeva-Ego专题](discussions/physical-rsi-sept24.md)可作为“研究自动化、self-play、上下文经验、经验生成链路”四个边栏；不要把企业博客和论文实证合并成统一排行榜。Zeva-Ego的PIM明确在新实例清空，应放在同实例适应边界下。

如果从综述转向实验，使用[loss-first与记忆执行包](experiments/rlt-contact-memory/README.md)：先明确测得后果、部署输入与监督梯度，再逐级验证预测、在线控制、跨实例经验复用。它是本项目提案，不能写成上述工作已经共同证明的结论。

- 一张分层系统图：策略、记忆/技能、目标/数据、改进器四层，标明可修改对象与固定约束；以 SVG 等可编辑矢量格式保存。
- 一张闭环成本图：同时标注采集、复位、验证、训练、人类接管的预算，避免仅报 GPU 时间。
- 一张证据矩阵：论文为行，留存范围、人工条件、物理平台、评价独立性、递归对象为列。
- 一张多轮评价示意：累计交互预算对新任务、旧任务、恢复能力分别作曲线；没有原始数据时只画清楚标注的概念图。

写作时每段先提出可检验的问题，再用两到四篇工作比较机制与条件，最后说明哪些证据仍缺失。不要把论文卡片直接串成摘要合集。
